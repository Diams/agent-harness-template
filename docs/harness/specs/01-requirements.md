# 要求文書: agent-harness-template

- 工程: 1. 要求整理
- 状態: 確認済み
- 更新日: 2026-11-01

## 1. 目的

エージェントの振る舞い、スキル、git 運用、開発プロセスを 1 つのリポジトリにまとめ、新しいプロジェクトでも同じ環境をすぐに使えるようにする。

## 2. 想定利用者

- 主な利用者: テンプレートの作成者本人
- 次の利用者: 公開テンプレートとして使う他の開発者

## 3. 機能要求

| ID | 要求 | 受け入れ条件 |
|---|---|---|
| F1 | テンプレートから簡単に使い始められる | 手順は README の数ステップに収まり、追加ツールは不要 |
| F2 | 利用先で固有の設定を追加できる | 共通部分とプロジェクト固有部分のファイルが分かれている |
| F3 | テンプレート本体の更新を利用先に取り込める | 取り込み手順が README にあり、コンフリクトが起きにくい構成になっている |
| F4 | エージェントの振る舞いを定義できる | 口調、判断基準、禁止事項などが 1 か所にまとまっている |
| F5 | スキルを定義できる | 追加手順が決まっており、初期スキルを同梱している |
| F6 | Claude Code と GitHub Copilot の両方で動く | 同じ指示とスキルが両方で読み込まれることを確認済み |
| F7 | git の運用方法を定義する | ブランチ、コミット、PR、マージのルールが文書化されている |
| F8 | 開発プロセスを定義する | 各工程の手順と完了条件が文書化されている |
| F9 | エージェントが定義に従って動く | 文書だけでなく、指示やスキルから参照されている |

## 4. 非機能要求

- 一元管理: 同じ内容を複数の場所に書かず、更新漏れを防ぐ。
- 技術スタック非依存: 特定の言語やフレームワークを前提にしない。
- クロスプラットフォーム: Windows、macOS、Linux で動く。
- 安全性: 秘密情報を含めず、公開しても問題ない内容にする。

## 5. 対象外

- アプリケーションのコード雛形
- GitHub 以外のホスティング(GitLab など)
- Claude Code と GitHub Copilot 以外のツールへの正式対応

## 6. 決定事項

### 6.1 リポジトリと配布

- GitHub の Public リポジトリとし、文書は日本語で書く。
- 新しいプロジェクトは `Use this template` で始める。
- ハーネス自体のカスタマイズやテンプレートへの改善提案にはフォークを使う。
- テンプレートの更新を取り込む手順を README に記載する。自動化は必要になってから検討する。

### 6.2 ツール対応

- 指示は `AGENTS.md` のみに置き、`CLAUDE.md` と `.github/copilot-instructions.md` は置かない(要件定義時に変更)。
- Claude Code は v2.1.277 以降を必須とする。
- GitHub Copilot はまず VS Code と CLI を対象とし、クラウドエージェントは検証後に追加する。
- 指示、スキル、git 運用、開発プロセスは両ツールで同等にする。
- 権限、フック、サブエージェントはツールごとに対応する。

### 6.3 git 運用

- ブランチ戦略は GitHub Flow とする。
- コミットメッセージは Conventional Commits に従う。

### 6.4 開発プロセス

| 工程 | 内容 | 人間の確認(標準区分) |
|---|---|---|
| 1. 要求整理 | ユーザーの要求を整理する | 完了時に確認 |
| 2. 要件定義 | ユーザー要求からシステム要件を定義する | 完了時に確認 |
| 3. 設計 | システム要件から実現方法を検討し、システムを設計する | 完了時に確認 |
| 4. 実装 | 設計を基に実装する | なし |
| 5. テスト | 実装をテストする | なし |
| 6. AI レビュー | AI が要件、設計、差分を照合してレビューする | なし |
| 7. 人間レビュー | 人間がレビューし、承認後に `main` へマージする | 工程そのもの |

### 6.5 変更の区分

テストと人間レビューは原則として省略せず、上流の文書を省略する。判断に迷ったら標準として扱い、選んだ区分を PR に明記する。

| 区分 | 例 | 工程の扱い |
|---|---|---|
| 標準 | 新機能、仕様変更 | 全工程を実施する |
| 軽量 | 動作やインターフェースが変わらない修正、仕様が明確なバグ修正 | 工程 1 は PR の説明欄に記載し、工程 2、3 は省略する |
| 文書のみ | 誤字、README の修正 | 工程 1 は PR の説明欄に記載し、工程 2〜5 は省略する |
| 緊急 | 本番障害 | 工程 1〜3 は事後に実施する |

### 6.6 初期スキル

| スキル | 対応工程 | 成果物 |
|---|---|---|
| `elicit-requirements` | 1. 要求整理 | 要求文書 |
| `define-requirements` | 2. 要件定義 | 要件定義書 |
| `design-system` | 3. 設計 | 設計書 |
| `implement` | 4. 実装 | コード |
| `run-tests` | 5. テスト | テストと結果 |
| `ai-review` | 6. AI レビュー | レビュー結果 |
| `commit-and-pr` | git 運用 | コミット、PR |
| `setup-project` | 利用開始 | プロジェクト用の `README.md`、`PROJECT.md`(公開後に追加) |

次の内容はスキルにしない。

| 内容 | 置き場所 |
|---|---|
| 7 工程の概要、区分の判定基準、GitHub Flow の基本ルール | `AGENTS.md` |
| PR の説明欄の形式 | PR テンプレート |
| テストやビルドのコマンド | プロジェクト固有のファイル |

レビューの指摘には `implement` に戻って対応する。

## 7. 次工程への引き継ぎ

- Claude Code と GitHub Copilot の現行仕様を公式ドキュメントで確認する。対象は指示、スキル、サブエージェント、権限、フックの読み込み場所と対応環境とする。
- `ai-review` を実装時とは別の文脈で実行する方法を、ツールごとに確認する。
- 仕様の確認結果によって決定事項を変更する必要があれば、人間に確認する。
