# 開発プロセス

## 工程

| 工程 | 入力 | 成果物 | 完了条件 |
|---|---|---|---|
| 1. 要求整理 | ユーザーの依頼 | `docs/specs/<id>/requirements.md` | 目的、範囲、受け入れ条件が明確で、人間が確認した |
| 2. 要件定義 | 要求文書 | `docs/specs/<id>/system-requirements.md` | 全要件に検証方法があり、要求と対応し、人間が確認した |
| 3. 設計 | 要件定義書 | `docs/specs/<id>/design.md` | 全要件の実現方法と判断理由があり、人間が確認した |
| 4. 実装 | 設計書、または PR の説明欄 | コード | 設計の範囲をすべて実装した |
| 5. テスト | 受け入れ条件、`PROJECT.md` のコマンド | テストと結果 | 全テストが成功し、受け入れ条件を確認した |
| 6. AI レビュー | PR の差分、要件、設計 | PR 上のレビュー結果 | 「必須」の指摘が残っていない |
| 7. 人間レビュー | PR | 承認とマージ | 人間がマージした |

`<id>` は `YYYYMMDD-<topic>` とする。文書の先頭に「状態」を書き、人間の確認を得たら「確認済み」にする。

## 変更の区分

| 区分 | 対象 | 工程の扱い |
|---|---|---|
| 標準 | 新機能、仕様変更 | 全工程を実施する |
| 軽量 | 動作やインターフェースが変わらない修正、仕様が明確なバグ修正 | 工程 1 は PR の説明欄に記載し、工程 2、3 は省略する |
| 文書のみ | 誤字、README の修正 | 工程 1 は PR の説明欄に記載し、工程 2〜5 は省略する |
| 緊急 | 本番障害 | 工程 1〜3 は事後に実施する |

- 迷ったら標準とする。
- 選んだ区分を PR に明記する。
- 工程 1〜3 完了時に止まる確認点は標準区分に適用する。他の区分では PR の人間レビューで確認する。

## 緊急区分の進め方

1. 工程 4〜7 を実施して修正をマージする。PR の説明欄に事後対応の予定を書く。
2. マージ後、工程 1〜3 の文書を別の `docs:` PR で追加する。

## 戻り

- テストの失敗や AI レビューの「必須」の指摘には、`implement` に戻って対応する。
- 要件や設計の変更が必要になったら、該当する工程に戻り、変更内容について人間の確認を得る。
